# Decisions and risks

Status: proposed defaults for review. No implementation decisions have been exercised on this machine.

## Proposed defaults

| Decision | Proposal | Rationale |
|---|---|---|
| Initial platform | Windows 11, Python | Matches the source; reduces first-prototype complexity |
| Speech stack | faster-whisper, large-v3-turbo, CUDA FP16 | Source recommendation; validate quality and actual GPU compatibility |
| Input mode | Push-to-talk | Explicit capture boundaries and predictable activation |
| Language | Auto, with English and Chinese overrides | Mixed-language use is the central requirement |
| Cleanup | Narrow grammar-only mode implemented (`qwen3.5:4b`, strict prompt + output-safety check); full "Clean mode" (filler removal/rephrasing) remains unresolved | See DECISIONS_AND_RISKS.md — grammar-only framing held up in testing where filler-removal framing did not |
| Delivery | Clipboard retained; controlled paste from V0.2 | Reliable manual fallback and no transcript loss on paste failure |
| Runtime storage | `%LOCALAPPDATA%\LocalVoice` | Keeps sensitive runtime files outside this OneDrive workspace |
| Audio/history | No saved audio; history off by default | Minimizes persistence while keeping history available by choice |
| Enabled history retention | Seven days; 24 hours and never as options | Explicit bounded default when history is enabled |
| External network | None, except loopback-only traffic to the local Ollama cleanup endpoint | Downloads and updates are separate explicit setup actions; a strict no-socket setting remains available and disables the cleanup adapter entirely |
| Overlapping jobs | One utterance; no automatic queue | Prevents stale or surprise pastes |
| Recording cap | 120 seconds initially | Bounds memory and accidental long capture |
| Updates | Manual initially | Reconcile distribution and offline requirements before automation |

## Risks and mitigations

| Risk | Impact | Mitigation / decision trigger |
|---|---|---|
| ASR loses code-switching or translates spans | Core product fails its purpose | Evaluate mixed-language corpus first; compare settings/models before UI work |
| Cleanup changes facts or negation | Incorrect communication | Conservative prompt, raw-text access, failure fallback, bilingual release review |
| Measured 2026-09-26: full "Clean mode" framing (filler removal + rephrasing) causes `qwen3.5:4b` and `gemma3:4b` to drop redundant bilingual content (e.g. "就是 还没到" disappeared entirely) and/or mistranslate connector words, even under strict anti-translation instructions; `qwen3:4b` preserves content correctly but ignores `think:false`, emitting a large, uncontrolled `<think>` reasoning block (45-53s / 1,600-6,469 tokens for one sentence) | Full Clean mode unusable as configured: wrong/lossy output (qwen3.5, gemma3) or unacceptable latency (qwen3) | Grammar-only mode (narrower scope, see cleanup.py) shipped as a safer subset with an output-safety check. Full Clean mode stays unimplemented until: more Qwen tags/quantizations and non-Qwen alternatives are tested, a prompting/parameter combination suppresses qwen3's thinking, and latency/quality are measured against a real bilingual corpus rather than single sentences. Literal mode remains the default until then. |
| **Added 2026-09-27, user-requested:** cross-session memory (`local_voice/memory.py`) is a new, narrower exception to the "no history by default" privacy stance (REQUIREMENTS.md P04). It persists a bounded list of abstracted facts (not raw transcripts), on by default | Any persistence beyond the current session is a privacy-relevant change from the original design; a user reviewing this later without reading this decision could be surprised by it | Deliberately scoped to abstracted facts, not transcripts, per explicit user direction ("context should be high-level abstract info, rather than raw text"); capped at 30 entries / ~80 chars each with substring-overlap deduplication; extraction prompt only fires on proper nouns/recurring terms, verified live to correctly skip ordinary sentences; `scripts/manage_memory.py` gives visibility/deletion control, matching F10's transparency principle even though this isn't F10 itself |
| ASR and LLM contend for VRAM | Delays or crashes | Measure simultaneous memory use; evaluate smaller quantization, unloading, or cleanup-off mode |
| Windows focus or integrity rules block input | Missing or misplaced text | Focus recheck, no forced elevation, single paste attempt, retained clipboard |
| Hotkey conflicts with AltGr or another app | Lost typing or unintended activation | Configurable binding and layout-specific checks |
| An active Chinese IME (e.g., Microsoft Pinyin) intercepts the hotkey, or holds a candidate window/focus state that automatic paste does not account for | Hotkey fails to trigger, or paste lands while an IME candidate window is open, corrupting the target field | Test push-to-talk and auto-paste with common Windows Chinese IMEs enabled; recheck target/composition state before paste; fall back to clipboard-only delivery when IME state is uncertain |
| Silence yields hallucinated text | Unwanted output | Silence gate/VAD, empty-result handling, no automatic paste of rejected output |
| **Found and fixed 2026-09-27:** a longer dictation (~18s, confirmed by log timing to have been captured in full) only produced the ending portion of the speech -- audio capture was not at fault (recorded duration matched the physical hold time almost exactly) | Long dictations could silently lose their beginning, with no error and a plausible-looking (just incomplete) result | Disabled `condition_on_previous_text` (was defaulting to `True`) in the transcribe call -- a well-documented cause of exactly this failure: conditioning each segment on prior decoded text lets an early misstep (background noise, the hotkey's own keypress sound, hesitation) cascade into skipped/corrupted later segments. Verified no regression on the existing smoke test; not yet verified against a real reproduction of the original failure, since it depends on the user's live voice. |
| Local files sync through OneDrive | Privacy expectation violated | Keep runtime data outside project; inspect actual paths during testing |
| Clipboard history/sync exposes text | Local processing does not guarantee local retention | Explain OS clipboard boundary; retain source-requested fallback behavior transparently |
| Implicit runtime download/update | Offline promise fails | Explicit setup, local-path loading, fail clearly for missing assets, traffic audit |
| Worker stalls or device disappears | App becomes unusable | Cancellation IDs, finite timeouts, restartable worker, recoverable device state |
| **Resolved 2026-09-27:** M2's `SendInput`-based auto-paste failed every call with `ERROR_INVALID_PARAMETER` (87). Root cause: the ctypes `INPUT` union only declared the `KEYBDINPUT` member (32-byte struct), but Windows validates the `cbSize` argument against the real union's size, which is set by its *largest* member, `MOUSEINPUT` (40 bytes on x64) | Auto-paste silently never worked; text always stayed clipboard-only regardless of settings | Added an unused `MOUSEINPUT`-shaped field to the union purely so `ctypes.sizeof()` matches Windows' expectation (40 bytes); also switched `dwExtraInfo` from a pointer to a plain `ULONG_PTR`-sized integer. Verified by injecting into an isolated test window with a real message pump and reading back the result. |
| **Found 2026-09-27:** running two instances of the app simultaneously (one launched for testing, one by the user) causes both to listen to the same global hotkey and race to write the same clipboard, producing what looks like "sometimes pastes old text" | Confusing, hard-to-diagnose stale output | Always confirm only one instance is running (`Get-CimInstance Win32_Process -Filter "Name='python.exe'"`) before debugging clipboard/paste issues; a single-instance lock (e.g. a named mutex at startup) would be a reasonable M4/M5 hardening item |
| **Found 2026-09-27, fix confirmed live:** Whisper decoded confirmed-correct Chinese speech (detected `zh` at high confidence) as romanized pinyin ("Shu Dao Nan...") instead of Han characters — a documented Whisper behavior distinct from a language-detection failure | Chinese output unusable even though detection worked | Added a short Chinese-character `initial_prompt` to the transcribe call. Confirmed live: output switched to Han characters. |
| **Found 2026-09-27:** even with Han characters restored, homophone/character-choice errors remain on rare/obscure content (tested with classical poetry: 数到难→蜀道难, 老计福利→老骥伏枥, etc.) — the local grammar-only cleanup model doesn't correct these by design (out of scope for that prompt), and genuinely fixing them requires either a much larger model or explicit step-by-step reasoning (`think:true` on qwen3.5:4b got every correction right, but took 64s/7,270 tokens for one passage — confirmed too slow for interactive use) | Rare names/vocabulary/obscure content can transcribe with plausible-sounding wrong characters | User chose to stay fully local rather than add a cloud LLM fallback (a real capability gap vs. cloud competitors like Typeless, which send full session context to frontier-scale cloud models — see chat log 2026-09-27). Implemented instead: session context (last 3 delivered dictations, in-memory only, never persisted/logged) passed to the grammar-cleanup prompt, with a narrowly-scoped added rule ("fix a name/term to match the reference context only when clearly the same word mistranscribed, never guess otherwise"). Verified live: correctly fixed "馬有友"→"馬友友" when "马友友" appeared in prior context, left it alone without that context, stayed fast (0.2-0.4s, no reasoning mode needed). This helps recurring names/topics within a session; it does not fix one-off obscure content with no prior context (e.g. still can't fix a poem recited from a cold start). |
| **Resolved 2026-09-26:** `ctranslate2`'s GPU backend loaded the model successfully but failed at actual transcription with `Library cublas64_12.dll is not found or cannot be loaded` — the NVIDIA driver alone does not ship cuBLAS/cuDNN; those come from the CUDA Toolkit, which is not installed here | Would have looked like a working setup (model load succeeds) until first real use, or silently fallen back to CPU on `device="auto"` | Installed `nvidia-cublas-cu12` and `nvidia-cudnn-cu12` pip wheels (~1.3 GB) into the `local-voice` env instead of the full CUDA Toolkit installer; `asr_worker.py` locates their `bin/` directories via `importlib.util.find_spec` and adds them to `PATH`/`os.add_dll_directory` before importing faster-whisper, since Windows does not search `site-packages/nvidia/*/bin` by default. Confirmed fixed by re-running the transcription smoke test. |
| Packaging native libraries is fragile | Installation fails on another PC | Clean-machine packaging gate and pinned compatibility matrix |
| Model/library license obligations overlooked | Distribution blocked | Review official licenses before packaging or redistribution. **Resolved 2026-09-27:** Apache 2.0 chosen for this project itself, at explicit user request; `LICENSE` added at repo root. |
| **Decided 2026-09-27:** Windows installer approach — a single frozen PyInstaller `.exe` bundling CUDA/`ctranslate2` was considered but rejected: native-extension bundling inside PyInstaller is a known fragile area, and `asr_worker.py`'s DLL-location logic (`importlib.util.find_spec` against a normal site-packages layout) would need untested rework inside a frozen bundle | A from-scratch repackaging approach risked burning significant time for uncertain payoff, with no way to validate on a second machine | User chose the lower-risk path: a small (~2 MB) Inno Setup installer (`installer/local_voice.iss`) with a `setup_env.ps1` post-install step. See the next row for what actually shipped in that script. |
| **Found and fixed 2026-09-27:** the first `setup_env.ps1` used the official python.org installer (a WiX Burn bundle) to acquire Python when none was found. Live installer testing (both interactively by the user and by re-running the script directly) repeatedly failed with "pythonw.exe is missing" despite the installer reporting exit code 0. Root cause: WiX Burn bundles track "already installed" state across *multiple independent registry locations* (`HKCU\Software\Python\PythonCore\<ver>\InstallPath`, an Add/Remove Programs entry, and a separate `HKCU\Software\Classes\Installer\Dependencies\CPython-<ver>` provider key) — clearing one during debugging still left the bundle believing Python was present via another, so it silently no-op'd (no files placed) instead of installing | The installer appeared to succeed but the app could not run; genuinely confusing to diagnose without dedicated logging, since the script's own success/failure checks were the only signal | Rewrote `setup_env.ps1` to use the official **embeddable distribution** instead (a plain zip, no installer, no registry, no hidden state) when no suitable existing Python is found: extract directly into `{app}\venv\Scripts`, enable site-packages via the `._pth` file, bootstrap pip via `get-pip.py`, then install the same pinned requirements. Also added a persistent transcript log (`installer\setup_env.log`) and a clear failure `MsgBox` pointing to it, since the original script's failures were otherwise silent. Validated by running the fixed script directly from a clean state (twice) and launching the tray app through the resulting environment successfully. The fully-compiled installer `.exe` itself could not be re-validated end-to-end through automated non-interactive invocation in this environment (it consistently hung, apparently on an interactive consent step an unsigned installer triggers that has no interactive desktop to resolve against) — needed a normal interactive run by the user as the final check, which surfaced the next bug (below). |
| **Found and fixed 2026-09-27 (same session, one more round):** a real user run of the fixed installer above still failed the same way. Root cause this time: the embeddable-Python branch had no "already set up" check (unlike the existing-Python branch, which correctly skipped re-creating an existing venv) -- it unconditionally re-downloaded and re-extracted every time. Since the installer's `[Code]` hook runs `setup_env.ps1` on every invocation and auto-launches the app after a successful install, a second run -- while the app from the first run was still holding its own `pythonw.exe` open -- failed trying to overwrite it ("Access to the path ... is denied") | The fully-working fix from the row above still produced a user-visible failure on the very next real-world action (re-running or the auto-launch racing a second invocation), because idempotency was never actually tested, only the cold-start path | Added an upfront check: if `venv\Scripts\python.exe` and `pythonw.exe` already exist, skip Python acquisition entirely and go straight to a (fast, idempotent) `pip install` check. Also stop any running instance from that specific install directory before touching its files, so even a forced re-setup is safe. Verified live: fresh install, immediate re-run, and re-run *while the app was actively running* (the exact failure scenario) all now succeed. |
| **Found and fixed 2026-09-27, severe:** after the installer finally worked end-to-end, live testing produced garbled/hallucinated transcription output ("worked once partially, then random unrelated text"). Root cause: `huggingface_hub` 1.33.0 (pulled in transitively via `faster-whisper`, no explicit pin) defaults to a newer Xet-based chunked-download path that **silently failed to materialize any real content** -- `model.bin`'s snapshot symlink pointed through another symlink to a blob path that never actually existed on disk (total cached bytes: ~3.5 MB, vs. the real ~3 GB file), yet `WhisperModel(...)` reported success loading in ~3 seconds with **no error anywhere**. `ctranslate2` then ran inference against effectively missing/garbage weight data. Uninstalling the optional `hf-xet` accelerator package did not help -- the broken chunked-download path is apparently now a built-in default in this `huggingface_hub` version, not solely gated by that optional package | The single most severe bug this session: no error, no warning, a model that "loads fine" and partially appears to work, producing plausible-looking but fabricated transcription content -- exactly the kind of failure a user could easily mistake for their own speech being misheard rather than the model running on essentially no weights | Set `HF_HUB_DISABLE_XET=1` (via `os.environ.setdefault`, so a real environment variable can still override it) in `asr_worker.py` before importing `faster_whisper`, forcing the classic, well-tested plain-HTTP download path. Verified by clearing the cache and reloading twice: once still broken (confirming XET is not disabled merely by removing `hf-xet`), once fixed (real download took 68s and produced a correctly-sized 3,087,284,237-byte `model.bin`; a repeat smoke test then produced exactly correct transcription). This affects any fresh model download on any machine running this dependency stack, not just this one -- a real, generally-applicable fix, not a local quirk. |
| **Added 2026-09-27, user-requested:** `local_voice/updater.py` checks GitHub Releases for a newer version — another narrow, explicit exception to "no automatic external network activity" (REQUIREMENTS.md P06), same treatment as memory.py | Same category of risk as the memory feature: an automatic network call the original design didn't have | At most once per day automatically (cached locally), gated by `settings.check_for_updates` (default True, per explicit request), plus a manual "Check for updates" tray menu item; never blocks startup, never raises on failure (offline is a normal, silent no-op) |
| **Decided 2026-09-28, user-requested:** add an opt-in cloud grammar-cleanup backend, after concluding (from the Typeless architecture research earlier in the session) that the local model's remaining homophone/context-correction gaps are a genuine capability ceiling, not a prompting problem. Compared two different fixes: **gpt-4o-transcribe** (replace ASR itself, could fix errors at the source) vs. **a cloud LLM cleanup step** (fix Whisper's text output after the fact). Chose the cleanup-step approach: it only sends already-transcribed *text*, never audio, preserving the one privacy property (audio never leaves the device) this project was originally built around, and it keeps a working local fallback if the API is unavailable -- replacing ASR itself would remove local operation from the core feature entirely, not just an optional enhancement | Sending audio to a cloud ASR API would have been a much larger, harder-to-reverse departure from P01 than sending text for cleanup | User picked **Claude Haiku 4.5** over GPT-5-mini/Gemini Flash, reasoning that instruction-adherence (not raw capability) was the actual bottleneck seen locally, and smaller frontier models are typically strong at exactly that; no direct benchmark comparison was run for this specific task. Implemented as `local_voice/cloud_cleanup.py`, same prompt and safety-validation logic as the local version (imported, not duplicated), off by default (`settings.cleanup_backend = "local"`). The model id is a pinned dated snapshot in settings, not a floating alias, so a future Haiku 5.5 release requires a deliberate one-line config change plus a retest, never a silent behavior change -- the same reasoning applied throughout this session to not blindly trust an upgraded dependency's behavior. Unit-tested with a mocked client (error handling, output-safety rejection, context inclusion, model-id pass-through); **not yet tested against the real Anthropic API**, since that requires the user's own API key. |
